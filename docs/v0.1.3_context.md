### Phase 3 — Diagnosis: Stage 3 Schema Bug

We extracted Stage 3 errors from the audit JSON:
```
[stage3_error: ValidationError: 2 validation errors for Schema
  properties.extracted_salary_min.type
  Input should be 'TYPE_UNSPECIFIED', 'STRING', 'NUMBER', 'INTEGER', 
  'BOOLEAN', 'ARRAY', 'OBJECT' or 'NULL']
```

**Root cause found:** `backend/scoring/stage3_deep_eval.py:118` used JSON Schema's `type: ["integer", "null"]` syntax. Gemini's schema dialect rejects this — requires single uppercase enum string + separate `nullable: true` flag.

**Fix applied:**
```python
# Before:
"extracted_salary_min": {"type": ["integer", "null"]},
"extracted_salary_max": {"type": ["integer", "null"]},

# After:
"extracted_salary_min": {"type": "integer", "nullable": True},
"extracted_salary_max": {"type": "integer", "nullable": True},
```

### Phase 12 — REAL Bug Found: Worker Daily Cap

**The Worker had `DAILY_CALL_CAP = 250` per UUID per day.** A single full search needs:
- Stage 1 anti-pattern: ~160 calls
- Stage 2 triage: ~120 calls
- Stage 3 deep eval: ~50 calls
- **Total: ~330 calls per search**

The cap was BELOW the cost of one search. Every run hit the cap mid-Stage-2.

**Bigger insight:** Stage 2 score = 50 for 88 roles is the **Flash fallback when its API call errors**. So the previous run with 88 qualifying / 1 STRONG / 12 GOOD was ALSO partially using fallback values — we just hadn't noticed.

**Fix applied:**
```typescript
// cf_worker/src/index.ts
const DAILY_CALL_CAP = 2000;  // was 250
```

Worker redeployed via `wrangler deploy`. User UUID counter reset:

## 🐛 Bugs Found and Fixed

### 1. Gemini Schema Validator (`stage3_deep_eval.py:118`)
- **Symptom:** 100% of Stage 3 calls fail with `ValidationError: properties.extracted_salary_min.type`
- **Root cause:** Used JSON Schema's `type: [list, types]` syntax for nullables, which Gemini doesn't support
- **Fix:** Use `{"type": "integer", "nullable": True}`
- **Status:** FIXED in current backend.exe

### 2. Worker Daily Cap (`cf_worker/src/index.ts`)
- **Symptom:** All searches hit 429 "daily_cap_exceeded" mid-run
- **Root cause:** `DAILY_CALL_CAP = 250` < 330 calls per search
- **Fix:** `DAILY_CALL_CAP = 2000`
- **Status:** FIXED, deployed via wrangler

### 3. Stage 2 Fallback Score 50 (revealed by audit)
- **Symptom:** 88 roles in latest run had Stage 2 score = exactly 50
- **Root cause:** Flash's fallback when API errors
- **Fix:** Implicit — the cap fix prevents the underlying API errors
- **Note:** Earlier "good" runs (88 qualifying / 1 STRONG / 12 GOOD) were ALSO using fallback; just less obvious

### 4. Frontend Hardcoded to 4 Sources (Keywords.tsx, Run.tsx)
- **Symptom:** Backend has 14 active scrapers but frontend only requested 4

## 🧠 Hard-Won Insights (preserve these!)

1. **Gemini schema dialect ≠ JSON Schema spec** — uses single-string `type` enum, `nullable: true` flag (not `type: ["x", "null"]`)
2. **Stage 2 score 50 = Flash fallback when API errors** — NOT a real evaluation. Watch for distributions clustered at 50.
3. **Worker daily call cap must accommodate full search** — minimum 1500-2000/day per UUID for testing. 250 is unusable.
4. **The "88 qualifying" baseline run was already partially degraded** — Flash fallback hit there too, just less obviously
5. **Workday returns broad/loose matches when given keyword search** — needs post-fetch token-overlap filter. Same for iCIMS/TheMuse.
6. **Substring matching kills near-keyword matches** — "AI Enablement Lead" won't match "AI Enablement Manager" with `kw in searchable`. Use Greenhouse's `_matches_any_keyword`.
7. **Tauri progress callbacks don't propagate without explicit wiring** — runner → score_roles → api.py state mutation. State stays at step 1 forever otherwise.
8. **Empty-JD scrapers (Workday/iCIMS/TheMuse)** — JDs are lazy-fetched in runner step 4.5. Matcher applied at scrape stage sees title only. Lower title threshold to 0.50 for these.
9. **OneDrive-synced project folder + Tauri = file lock issues** — running app.exe holds binary file open; can't rebuild/copy without killing it first
10. **CMD vs PowerShell**: User is in cmd.exe by default. PowerShell cmdlets (Get-Process, New-Item) won't work — use tasklist, mkdir, etc.
11. **Tauri dev needs `npm run tauri dev` restart for backend changes** — Vite hot-reload only handles frontend. Backend.exe is the bundled PyInstaller build; new binary requires restart.
12. **Cancel logic is verified correct** — runs.db row deleted, cost tracker run_summary marked cancelled, no orphan data persisted
13. **Auto-deploy on push is dangerous during iteration** — adopted tag-only release gate (push runs CI build only; tagging publishes)
14. **macOS-13 Intel runners chronically queue-starved** — drop from default matrix, re-enable on demand
15. **Tauri 2 schema validators are stricter than JSON Schema** — affects Pydantic validation of the request before API call fires
16. **The keyword generator outputs job titles, not search terms** — fundamental mismatch with how scrapers query APIs. 35 of 40 keywords yield zero matches.
17. **Stage 3 schema gate is upstream of API call** — Pydantic validates schema definition; failing schema means API never sees the request
18. **Cache hit replays previously-completed runs** — cleared via `del runs.db*` + clearing `runs/` folder
19. **Profile + scrape + score = ~330 LLM calls/run** — must architect cap accordingly
20. **Testers don't have API keys for keyed sources** — USAJOBS, Adzuna, Findwork no-op silently for them. Future Worker proxy work could backfill.
